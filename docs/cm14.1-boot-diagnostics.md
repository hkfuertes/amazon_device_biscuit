## ADB-only probe

Generator (offline, no device operations):

```sh
python3 scripts/diagnostics/make-adb-boot-probe.py
```

Bounded read-only observer (launch detached before a separately authorized reboot):

```sh
nohup python3 scripts/diagnostics/observe-biscuit-boot.py '<test-label>' \
  </dev/null >/tmp/biscuit-boot-observer.log 2>&1 &
```

The observer does not flash, reboot, or recover the device. For the last test, a
separate one-shot host guard waited 45 seconds, confirmed absence of the target's
ADB transport and of another helper, then launched only the authorized root-owned
`boot-recovery.sh`. This caught the next preloader cycle without another blind boot.

Artifacts and logs: `workspace/diagnostics/cm14-adb-boot-probe/` (git-ignored).
The generator pins input hashes and verifies CPIO round trips, boot IDs, unchanged
kernel payload/cmdline/other components, ZIP integrity, and boot-only installer scope.
The explicit `-raw` variant removes exactly one validated 512-byte MTK header; it
preserves every byte of the underlying kernel/DTB payload. The `-raw-up` variant
changes only the header command line by appending `maxcpus=1`; its failed test does
not establish whether that command line reached the ARM32 kernel.
It reuses existing static ARM32 CM12 recovery binaries without compiling.
It does **not** launch the recovery UI or mount system, data, cache, or other blocks.
Only init, ueventd, and adbd run; the recovery multicall binary supplies the shell.
The public host key is embedded in `/adb_keys`; `ro.adb.secure=1` remains enabled.
The probes preserve their respective kernel addresses and architecture-specific
`bootopt`; therefore the comparison is kernel plus its required boot metadata, not
an identical-header cross-architecture comparison.

The positive control reports Linux 3.18.19 **aarch64** with ARM32 userspace.
The Fire OS 6 kernel is also Linux 3.18.19 but **ARM32**. Do not describe this as a
3.10-versus-3.18 comparison. The control's live command line has no `rdinit` override.
Its init/adbd startup and USB configuration are visible at approximately 2 seconds
in kernel time. Its mount table contains only rootfs, tmpfs, devpts, proc, sysfs,
selinuxfs, and FunctionFS.

### Host authentication pitfall

The initial control observer treated a failed `adb get-state` as absence, hiding
an `unauthorized` transport. Explicit `adb devices -l` and USB descriptors revealed
that the probe was running (`18d1:d001`, product `BootProbe`).
The public key embedded in the probe matched the current user's private-key-derived
public key, but the existing host ADB server was running as root. After confirming
ordinary-user read/write access to the USB node, `adb kill-server` and
`adb start-server` restarted it as the user; authentication succeeded without
changing the image, disabling authentication, deleting keys, or using sudo.
Subsequent observers distinguish unauthorized/offline/recovery/device states.

### Boot ID detail

The pinned CM12 boot image's SHA-1 ID covers kernel, ramdisk, and second stage.
The prior diagnostic image also includes the empty DT size. The generator detects
and preserves each verified format instead of assuming one universal variant.
This was caught by an assertion before a probe ZIP was generated; it is not a
proven cause of any device boot failure.

SHA-256 `794e039afa1f168601ebd73e28faaf1cef83e6dbeddeb862f75e4dcdbe4eaf53`.
The read-only copy is `installed-boot-a-payload.readonly.bin` in the diagnostic folder.
The payload includes both ARM32/ARM64 detection messages. The local source at
`/tmp/amonet-biscuit`, commit `fff316c`, selects the mode from the third `bootopt`
field and writes LK's mode flag. The installed bytes match the packaged payload;
source-to-binary equivalence for that local checkout has not been established.
The actual ARM32 branch execution and handoff registers are not observed.
No exploit or bootloader write was performed.

TWRP remaps `/dev/block/platform/soc/by-name/boot_a` to `boot_a_x` (`mmcblk0p10`).
An initial size guard rejected that alias before attempting a payload read.
Kernel sysfs identifies the real exploit partition as `mmcblk0p17`, `PARTNAME=boot_a`,
size 115,343,360 bytes. Only the packaged payload extent at offset 114,281,984
(`223207 * 512`) was read from it after validating identity and bounds.
Do not use the physical exploit partition as a ROM flash target.

## Read-only RAM-console capture (in progress)

`fireos6-stock-raw.last_kmsg` contains previous TWRP activity: `recovery` process
records and ARM64 addresses, not a demonstrated panic from the failed ARM32 probe.
The embedded configs of both Fire OS 6 kernels enable a 64-KiB DRAM RAM console at
`0x44400000`, with PSTORE disabled. The CM12 source uses the same address and the
same 16-u32 console header. Booting another ordinary kernel can overwrite evidence.
TWRP exposes no usable `/dev/mem`, `/dev/kmem`, `/proc/kcore`, or matching native
physical-memory interface. No generic memory node or incompatible module was added.

The isolated capture recipe is:

```sh
bash scripts/diagnostics/build-console-capture-kernel.sh
docker logs -f cm12-biscuit-build
# Only after a successful build:
python3 scripts/diagnostics/make-console-capture-boot.py
python3 scripts/diagnostics/decode-fireos6-console.py --self-test
```

The build runs detached, refuses to replace a running container, and stages only
under `workspace/diagnostics/cm12-console-capture-build/`. It reserves the original
console pages before allocator initialization, disables its own MTK RAM-console
writer, and compiles `scripts/diagnostics/fireos6-console-reader.c` into the kernel.
The proc reader permits only that fixed 64-KiB region, requires root mode 0400 and
`CAP_SYS_RAWIO`, checks valid/reserved pages and header bounds, and has no write path.
Its format/bounds self-check runs before creating the proc entry. The host decoder
also checks truncated/corrupt input and partial/wrapped circular-buffer ordering.
Neither stable ROM trees nor prebuilts are replaced.

The kernel-only build completed successfully (container exit 0). The packager reuses
the exact positive-control ramdisk and boot metadata, validates ARM64 Image magic,
the reader marker, load ranges, components and boot ID. It also preserves the
pinned control ZIP's boot-only installer byte-for-byte, replacing only `boot.img`.
The resulting image is 7,041,024 bytes, SHA-256
`3f8d0b03332ec82a4002ded5c782fb92fff8bd9159528696d2a389a06bc402ce`;
the ZIP SHA-256 is `b0d6a68be85ffc022100407b7ae751aee1f6b577b6574f3ee565011b30c761c3`.

A first attempt to avoid partition writes revealed that this amonet rejects
`fastboot boot` with `unknown command`: downloading succeeded, but Linux was never
started. This is not a failed capture-kernel boot test. The guard saw the existing
fastboot transport and took no action. The image was then installed through verified
TWRP, after another fresh backup; its full image-extent readback matched exactly.
The guarded reboot succeeded (`cm12-console-capture-flashed.*`): authenticated root
ADB on ARM64 Linux 3.18.19, with the reader's ready marker at 1.692224 seconds.
`/proc/biscuit_fireos6_console` is root-only 0400. A successful read returned exactly
65,536 bytes (SHA-256 `e4bc3c8ecef876d1f8380b5493cfc6d5319a35f175556f38e049a669228fb8a4`),
and a second full read was byte-identical. The decoded console contains 64,576
bytes, including 51 recovery-process records and ARM64 addresses, with timestamps
1.946676–274.963658 seconds. It is previous TWRP activity, not the failed ARM32
kernel and not the capture kernel's own log. The guard found the ADB transport
and did not launch a helper.

The capture kernel/reader are now a positive control. Preservation through a
fastboot reinstallation still needs a separate control before interpreting a new
ARM32 failure. The minimal ramdisk has no standalone `getprop`: identify it with
`/sbin/busybox cat /default.prop`, as the tracked observer already does. An ad-hoc
host check initially used the unavailable command; correcting that check required
no image, authentication, or permissions change.

Before this phase, a fresh 16-MiB backup matching the installed `-raw-up` probe was
saved as `pre-capture-phase.boot.backup.img` (SHA-256
`852c0a50c2cee958df85b9b24e83392462aa989539b47fd79c690cfb0d281694`).
The device then entered fastboot through TWRP's `reboot-amonet`. Saved
`fastboot-pre-capture.getvar.log` confirms amonet 1.1.0, slot `a`, and download limit
`0x6c00000`. The later unsupported RAM-boot command did not write partitions; its
log is `cm12-console-capture-control.fastboot-boot.log`.

Local LK disassembly plus that published limit implies a download scratch area at
`0x45000000` with the documented amonet size adjustment (`0x45100000` under the
unmodified local formula), both above console end `0x44410000`. This is static-code
and live-metadata consistency, not a direct observation of handoff registers or a
readback of installed LK. Any fresh failed-kernel capture should avoid intervening
TWRP, and captured logs still require kernel/architecture/timestamp provenance.
