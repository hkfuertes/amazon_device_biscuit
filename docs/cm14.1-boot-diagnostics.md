## ADB-only probe

Generator (offline, no device operations):

```sh
python3 scripts/diagnostics/make-adb-boot-probe.py
```

Bounded read-only observer (launch detached before a separately authorized reboot):

```sh
nohup python3 scripts/diagnostics/observe-biscuit-boot.py '<test-label>' \
  </dev/null >/tmp/biscuit-boot-observer.log 2>&1 &
```

The observer does not flash, reboot, or recover the device. For the last test, a
separate one-shot host guard waited 45 seconds, confirmed absence of the target's
ADB transport and of another helper, then launched only the authorized root-owned
`boot-recovery.sh`. This caught the next preloader cycle without another blind boot.

Artifacts and logs: `workspace/diagnostics/cm14-adb-boot-probe/` (git-ignored).
The generator pins input hashes and verifies CPIO round trips, boot IDs, unchanged
kernel payload/cmdline/other components, ZIP integrity, and boot-only installer scope.
The explicit `-raw` variant removes exactly one validated 512-byte MTK header; it
preserves every byte of the underlying kernel/DTB payload.
It reuses existing static ARM32 CM12 recovery binaries without compiling.
It does **not** launch the recovery UI or mount system, data, cache, or other blocks.
Only init, ueventd, and adbd run; the recovery multicall binary supplies the shell.
The public host key is embedded in `/adb_keys`; `ro.adb.secure=1` remains enabled.
The probes preserve their respective kernel addresses and architecture-specific
`bootopt`; therefore the comparison is kernel plus its required boot metadata, not
an identical-header cross-architecture comparison.

The positive control reports Linux 3.18.19 **aarch64** with ARM32 userspace.
The Fire OS 6 kernel is also Linux 3.18.19 but **ARM32**. Do not describe this as a
3.10-versus-3.18 comparison. The control's live command line has no `rdinit` override.
Its init/adbd startup and USB configuration are visible at approximately 2 seconds
in kernel time. Its mount table contains only rootfs, tmpfs, devpts, proc, sysfs,
selinuxfs, and FunctionFS.

### Host authentication pitfall

The initial control observer treated a failed `adb get-state` as absence, hiding
an `unauthorized` transport. Explicit `adb devices -l` and USB descriptors revealed
that the probe was running (`18d1:d001`, product `BootProbe`).
The public key embedded in the probe matched the current user's private-key-derived
public key, but the existing host ADB server was running as root. After confirming
ordinary-user read/write access to the USB node, `adb kill-server` and
`adb start-server` restarted it as the user; authentication succeeded without
changing the image, disabling authentication, deleting keys, or using sudo.
Subsequent observers distinguish unauthorized/offline/recovery/device states.

### Boot ID detail

The pinned CM12 boot image's SHA-1 ID covers kernel, ramdisk, and second stage.
The prior diagnostic image also includes the empty DT size. The generator detects
and preserves each verified format instead of assuming one universal variant.
This was caught by an assertion before a probe ZIP was generated; it is not a
proven cause of any device boot failure.

## Installed amonet provenance (read-only)

The 13,888-byte installed `boot.payload` matches
`/opt/amonet-biscuit-v1.1.0/amonet/bin/boot.payload` exactly:
SHA-256 `794e039afa1f168601ebd73e28faaf1cef83e6dbeddeb862f75e4dcdbe4eaf53`.
The read-only copy is `installed-boot-a-payload.readonly.bin` in the diagnostic folder.
The payload includes both ARM32/ARM64 detection messages. The local source at
`/tmp/amonet-biscuit`, commit `fff316c`, selects the mode from the third `bootopt`
field and writes LK's mode flag. Binary equivalence to the packaged payload is
verified; the actual ARM32 branch execution and handoff registers are not observed.
No exploit or bootloader write was performed.

TWRP remaps `/dev/block/platform/soc/by-name/boot_a` to `boot_a_x` (`mmcblk0p10`).
An initial size guard rejected that alias before attempting a payload read.
Kernel sysfs identifies the real exploit partition as `mmcblk0p17`, `PARTNAME=boot_a`,
size 115,343,360 bytes. Only the packaged payload extent at offset 114,281,984
(`223207 * 512`) was read from it after validating identity and bounds.
Do not use the physical exploit partition as a ROM flash target.
